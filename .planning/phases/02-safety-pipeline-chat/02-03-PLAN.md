   - Step 1: Input safety scan → pipeline.scan_input(request.message, current_user.id, request.model_id)
   - Step 2: If input blocked → record audit event → return ChatResponse(status="blocked", ...)

   - Step 7: If fail_closed at any step → record audit event → return ChatResponse(status="fail_closed", content="Your message could not be processed...")

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Frontend → API | Chat request crosses trust boundary — message and model_id must be validated |
| API → Model Provider | Model call only happens after input safety scan passes |
| Model Provider → API | Model response crosses trust boundary — output safety scan required before display |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-09 | Tampering | Chat request model_id | mitigate | Registry validates model_id against available providers; unknown model_id returns error |
| T-02-10 | Information Disclosure | Frontend blocked message | mitigate | BlockedMessage only displays API-provided block message text — never raw detected content per SAFE-04 |
| T-02-11 | Spoofing | Model provider credentials | mitigate | API keys from environment variables only — frontend never sees credentials |
| T-02-12 | Denial of Service | Model provider timeout | mitigate | httpx timeout=60.0 for model calls; if model hangs, request fails gracefully |
| T-02-13 | Elevation | Chat endpoint access | mitigate | Depends(get_current_user) ensures only authenticated users can chat; no anonymous access |
</threat_model>
